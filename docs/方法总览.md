# 微信 4.1.10.27 发送「真语音条」实测方案

> 记录时间：2026-10-23
> 目标客户端：微信 PC 4.1.10.27（Weixin.dll，ImageBase 0x180000000）
> 结论：**已实测可用** —— 通过自建 hook DLL 直接调用微信内部 ABI，发出的是真正的语音气泡（msgtype 34），不是 mp3 文件附件。

---

## 0. 一句话结论

微信的语音条发送在 4.1.10.27 里可以这样复刻：

```
构造语音消息对象（工厂 0x619A190 + 构造 0x619B3B0）
  → body+0xD8 写 34
  → BuildSendParam1(owner) 得到任务包装
  → BuildSendParam2(second, …) 得到第二参数
  → 调 send_message(0x1677A30)(first, second)
```

全部参数（目标 wxid、silk 字节、时长毫秒、Extra 常量）都已通过运行时探针实测确认。

---

## 1. 为什么必须自己造 hook

现成 hook（aixed/WeChat-Hook 系的定制构建）只暴露 3 个发送端点：

| 端点 | 状态 |
|---|---|
| `/SendTextMsg` | 有 |
| `/SendStickerMsg` | 有 |
| `/SendFileMsg` | 有 |
| `/SendVoiceMsg`、`/SendAudioMsg`、`/SendVideoMsg`、`/SendImgMsg`、`/SendEmojiMsg`、`/ForwardXMLMsg` | 全部 404 |

微信语音条不是普通文件：它是 `msgtype 34`，载荷是 **silk 编码**（腾讯私有格式，文件头 `0x02` + `#!SILK_V3`），并且要在发送时把「目标 + 原始音频字节 + 时长」交给微信自己的发送调度（CDN 上传在调度内部完成，不用自己实现）。

## 2. 关键 RVA（全部实测验证）

| RVA | 作用 | 证据 |
|---|---|---|
| `0x619A190` | 语音对象工厂：`Shared* f(Shared* out, const std::string* target, const std::string* silk, const uint32_t* durationMs, const Extra* extra)`，返回 `{body, owner}`（body = owner+0x10） | 分配 0x778 字节；`+0x1E1` 取 body；`+0x1F6` 调 ctor；`+0x277` 返回 out |
| `0x619B3B0` | 就地构造函数：RCX=self，RDX=目标字符串，R8=silk 字符串，R9D=时长，`[RSP+0x28]`=Extra | 内部写派生虚表 0x8DD0028；`0x619B68D` 把 this 放回 RAX |
| `0x6199D65` | `mov dword ptr [rax+0D8h], 22h`（写 msgtype=34） | 字节实测 `c7 80 d8 00 00 00 22 00 00 00` |
| `0x84EC9C8` | 发送任务虚表；`+0x10` 槽 = `0x1677A30` | 实读 `[0x84EC9C8+0x10] = ImageBase+0x1677A30` |
| `0x1677A30` | 通用 send_message 调度（文本/文件/表情/语音共用） | 文件发送也走这里 |
| `0x1649B50` | 把消息对象装进发送任务（原生路径里由 0x6199D10 调用） | 实测**策略 A 不需要它**也能发出去 |
| `0xDF40` | BuildSendParam2 依赖的辅助（`offset::create_param2`） | 与现有 wx_send.cpp 一致 |
| `0xA0CE0B0` | param2 用到的全局值地址 | 现有代码常量 |
| 文件对象对照 | 工厂 `0x1C4CE70`、构造 `0x18EEDC0`、body 虚表 `0x84F9748` | 与语音完全不同，**不能把文件的 49 改成 34 糊过去** |

`ImageBase = 0x180000000`，所有地址都是 RVA，运行时用 `GetModuleHandleW(L"Weixin.dll")` 加基址。

## 3. 语音对象 body 布局（实测）

`body = owner + 0x10`，owner 虚表 `0x8DCFF98`，body 虚表 `0x8DD0028`。

| body 偏移 | 类型 | 含义 | 证据 |
|---|---|---|---|
| `+0x00` | void* | body 虚表 0x8DD0028 | 构造时写入 |
| `+0xB0` | MSVC `std::string`（32 字节：SSO/指针, size@+0x10, cap@+0x18） | **接收目标 wxid** | 探针实测内容 `wxid_…`（19 字符，size=19，cap=31） |
| `+0xD8` | uint32 | **msgtype = 34** | `mov [rax+0xD8], 22h` |
| `+0x708` | MSVC `std::string` | **silk 音频字节** | 探针实测内容以 `02 #!SILK_V3` 开头，size 3152 / cap 3167 |
| `+0x728` | uint32 | **时长（毫秒）** | 探针实测 1800 / 1920 / 2520 / 3200 / 4720，与录音时长吻合 |
| `+0x730` | 16 字节 | Extra 起首 16 字节 | 构造时 `movups` |
| `+0x740` | byte | 标志 | 构造时写入 |
| `+0x748` | MSVC `std::string` | Extra 里的附加字符串 | 构造时写入 |

**Extra（`[RSP+0x28]` 指向）实测 64 字节：**

```
04 00 00 00 | 03 00 00 00 | 30 75 00 00 | 00 …（后 52 字节全 0）
   = 4           = 3           = 30000
```

## 4. 运行时探针怎么做（方法论）

不看运行时数据，纯静态分析会卡在「这几个字段到底是什么」上。我们的做法：

1. **自建 DLL**：从源码构建 `version.dll`（MSBuild + v145 工具集），保持原有发送功能不变。
2. **MinHook 挂钩 `0x619B3B0`**，挂前做三重校验：
   - 函数首 21 字节特征码
   - body 虚表首槽 == 析构函数 RVA（`0x17781D0` 对不上就换 0x8DD0028 那套判断）
   - `VS_FIXEDFILEINFO` 必须等于 4.1.10.27
3. **入口用汇编写**：`pushfq` + 全寄存器 + `xsave/fxsave`（带 XCR0 掩码）+ 保存 `GetLastError`，观察完原样恢复，最后 `jmp [trampoline]` 尾跳 —— **不猜参数、不动栈上参数、不改返回值**。
4. detour 里只往环形槽写，独立 worker 线程落盘（热路径不做 IO），命中 3 次自动 `MH_DisableHook`，且**不释放 trampoline**。
5. 采集内容：RCX/RDX/R8/R9D/[RSP+0x28]，以及 RDX/R8 指向的**内容**（按 MSVC std::string 解读：size@+0x10、cap@+0x18，cap>15 时正文在 `*(void**)ptr`）。

### 实测抓到的样本（三次）

| 次 | r9d | silk 大小 | 内容特征 |
|---|---|---|---|
| 1 | 2520 | 1651 | 空录（静音压缩后很小） |
| 2 | 4720 | 8301 | 长句 |
| 3 | 3200 | 5622 | 短句 |
| 4 | 1800 | 3152 | 「你好」，silk 头 `02 23 21 53 49 4c 4b 5f 56 33` |

RDX 内容实测 = `wxid_…`（19 字符，正是目标 wxid），R8 内容实测 = `\x02#!SILK_V3…`。

## 5. live 实现（策略 A，实测能发）

```cpp
// 1) 目标字符串与 silk 字符串：手工构造 MSVC std::string 的内存布局
struct NativeString {                 // sizeof == 32
    union { unsigned char sso[16]; unsigned char* pointer; };
    uint64_t size;                    // +0x10
    uint64_t capacity;                // +0x18
};
// cap > 15 时，*pointer 指向单独分配的字节块（正文），size 为真实长度

// 2) Extra：实测常量
struct Extra { uint32_t codec=4, mode=3, limit=30000; unsigned char reserved[52]{}; }; // 64 字节

// 3) 造对象
struct Shared { uintptr_t body, owner; };   // body == owner + 0x10
using CreateVoice = Shared*(*)(Shared*, const NativeString*, const NativeString*, const uint32_t*, const Extra*);
CreateVoice create = (CreateVoice)(base + 0x619A190);
create(&shared, &targetStr, &silkStr, &duration, &extra);

// 4) 写 msgtype（构造内部其实也会写，但显式补一次无害）
*(uint32_t*)(shared.body + 0xD8) = 34;

// 5) 任务包装 + 第二参数（照抄生产环境已验证的文件发送范式）
auto first  = WeixinSend::BuildSendParam1(shared.owner);
auto second = (uint64_t*)HeapAlloc(GetProcessHeap(), HEAP_ZERO_MEMORY, 0xE8);
WeixinSend::BuildSendParam2_Image(second);          // 内部走 0xDF40

// 6) 调度
using Dispatch = __int64(*)(uint64_t, uint64_t);
((Dispatch)(base + 0x1677A30))(first, second);
```

**实测结果**：接口返回 `nativeReturn=0x1`，微信不崩，**「文件传输助手」里出现 3.3 秒语音条并能播放**；连发两条也正常（可重复调用）。

注意点：

- 不要用 `std::string` 类型本身去构造（CRT 可能不同）—— 手工摆内存布局更安全；
- 分配用 `HeapAlloc(GetProcessHeap())`，这些对象**不释放**（一次性小对象，进程生命周期内可以接受；提前释放有异步 use-after-free 风险）；
- 单次调用要加互斥 + 冷却 + 每进程上限（我们设 1.5 秒冷却、200 条上限），防止无界泄漏和刷屏。

## 6. 音频侧：mp3/wav → silk

微信要 silk，不用自己写编码器，`pysilk` 就够：

```python
import pysilk                    # pip install pysilk
pcm = <24kHz / 16bit / 单声道 PCM 字节>
silk = pysilk.encode(pcm, sample_rate=24000)   # 输出自带 0x02 前缀
```

PCM 用 ffmpeg 转：`ffmpeg -y -i in.mp3 -ac 1 -ar 24000 -f s16le out.pcm`

时长：`len(pcm)/2/24000` 秒 → 毫秒。

## 7. 工程要点（踩过的坑）

1. **实际生效的 DLL 在客户端目录**（和 `Weixin.exe` 同目录），不是安装包的 vendor 模板；但模板也要一起换，否则宿主自修复会把 DLL 还原回官方版。
2. **目录 ACL 可能锁写**（Deny Write），换 DLL 前要先解锁（我们用的脚本备份 SDDL，可一键恢复）。
3. 换 DLL 要**完整退出微信客户端**；直接 force kill 有概率掉登录（实测会要求重新扫码/确认）。
4. **MSBuild 增量编译会坑你**：如果源文件 mtime 比 obj 旧，会跳过编译，产出看起来「改了没生效」。强制 touch 或清 `x64` 目录。
5. 编译工具集要匹配本机 VS 版本（我们用 VS2026 / MSVC 14.50 / `PlatformToolset=v145`；原脚本写死 v143 会失败）。
6. 发送调用返回值 `0x1` **不代表送达**，要以微信端实际收到为准（我们最终是人工看「文件传输助手」确认的）。

## 8. 风险

- 这是调微信内部 ABI，**跨版本必崩**（换版本要重新定位 RVA + 重新校验特征码）。
- 对象生命周期/异步所有权未完全摸清，所以本次实现宁可不释放内存。
- 反作弊/完整性校验存在未知，长期使用需自行评估。
- 一定要保留原版 DLL 备份和回滚路径；崩溃后先恢复 DLL 再启动客户端。

## 10. 已知问题：聊天模式下不可用（2026-10-23）

发语音在本方案里依赖两步：本地 TTS 生成音频 + 调 `/SendVoiceMsg`（靠脚本 `voice-send.py`）。
**聊天模式（social）下工具被策略过滤**（没有 `pwsh`、没有 `tts_speak`），所以脚本跑不起来；
助手模式（assistant）下工具齐全，正常可用。

- 接口层没问题：`/SendVoiceMsg` 在两种模式下都能返回 `nativeReturn=0x1`。
- 临时绕过：`wechat.workModes["<chat key>"] = "assistant"`，重启桥接。
- 正式修法：bridge 层加 `wechat_voice_say(text)` / `wechat_voice_send(path)` 原生工具，
  并在 `social-tool-restrict` 里对社交模式放行。
