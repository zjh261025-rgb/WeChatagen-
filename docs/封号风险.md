# 封号风险说明（必读）

> 本文不是免责套话，是把「这套东西为什么可能被封、什么行为会加速被封、怎么把风险压到最低」讲清楚。
> 结论先放前面：**用 hook 类方案跑机器人，账号随时有被封的可能，这是方案本身的性质，不是配置问题。**

---

## 1. 为什么会有封号风险

本方案做的事，本质上是**在微信客户端进程里注入自定义 DLL，并直接调用微信内部函数发送消息**：

- 用 `version.dll` 劫持的方式把模块加载进微信进程；
- 用 MinHook 改写客户端内部函数入口（探针）；
- 直接调用内部工厂 / 发送调度（`0x619A190` / `0x1677A30`）构造并投递消息。

这些都不是微信公开 API，属于**逆向和非官方调用**。腾讯没有义务兼容，也一直在做检测与对抗。

---

## 2. 微信可能从哪些维度发现异常

按「越靠近客户端越容易被发现」排序：

| 维度 | 说明 | 风险 |
|---|---|---|
| **客户端完整性** | 程序目录被改动（`version.dll` 被替换）、内存中出现非官方模块、关键函数入口被改写（inline hook 会改变函数首字节） | 高 |
| **调用栈特征** | 官方发消息一定从 UI 线程、经过完整校验链；hook 直接调内部 ABI，线程/调用栈/入参状态都和正常路径不同 | 中高 |
| **行为特征** | 回复速度秒回、7×24 在线、固定间隔、消息长度分布异常、从不使用表情/语音/图片等原生特性、群发/批量添加好友 | 高 |
| **消息内容模式** | 大量模板化文本、相同内容多群转发、诱导性/营销内容 | 高（内容风控独立于 hook） |
| **设备与登录** | 新注册账号、异地登录、频繁切换设备/IP、模拟器/多开 | 中高 |
| **频率与风控策略** | 短时间大量消息、被多人拉黑/举报、群内被踢 | 中 |

> 注意：**不 hook 也可能被封**（纯 UI 自动化的 wxauto 方案同样会被风控），只是 hook 方案多了「客户端完整性」这一层暴露面。

---

## 3. 现实中的后果分级

| 级别 | 表现 |
|---|---|
| 轻度 | 消息发送失败/需要重新登录、被限制加好友或进群、短时间内消息延迟 |
| 中度 | 临时封禁（数小时到数天）、被要求人脸/短信验证、部分功能受限 |
| 重度 | **永久封号**，账号内聊天记录与好友关系不可恢复（充值/支付相关功能可能受限） |

概率上：**老号、活跃度正常、行为克制的个人号**风险较低；**新号、批量行为、营销用途**风险显著升高。

---

## 4. 把风险降到最低的实践

### 4.1 账号隔离（最重要）

- **绝不要用主号跑**。用一张独立的小号，且这张号不要绑定重要资产（支付、工作、家庭群）。
- 小号先「养」一段时间：正常聊天、发朋友圈、加几个好友，有正常人类使用迹像之后再上机器人。

### 4.2 行为要像人

- 控制频率：机器人回复最小间隔 ≥ 5 秒，每分钟不超过 3~5 条，避免「秒回」；
- 随机化：回复加随机延迟、随机长短、偶尔不回复（沉默是正常行为）；
- 别群发：不要同一内容发多个群、不要自动加好友、不要主动私聊陌生人；
- 保留人工操作：偶尔用手机登录、发语音、发图片、点赞，让账号曲线看起来正常。

### 4.3 技术面收敛

- 只开必要功能：用不到语音/文件就别开对应 hook 能力，减少暴露面；
- 别改太多客户端文件：能不动 `version.dll` 以外的就别动；
- 别在客户端里留调试痕迹：探针用完就卸（本方案探针命中 3 次自动 `MH_DisableHook`，但 DLL 仍在进程里）；
- 保持版本固定：升级后 RVA 失效，硬跑可能直接崩，反而容易触发异常上报。

### 4.4 内容与合规

- 不做营销、不刷屏、不碰灰色内容（这本身就是内容风控的高危区）；
- 群聊里明确是机器人身份时，风险更低（冒充真人是举报的高发点）；
- 尊重群规，被踢/被拉黑是风控的重要信号。

---

## 5. 一句话总结

**这套方案在技术上完全可行（已实测能发真语音条），但它走的是非官方路径，账号风险无法归零。**
请用小号、控制频率、保持人类行为特征；一旦账号出现异常（要求验证、消息失败），立即停用机器人并恢复官方 DLL。

本项目仅用于技术研究与自建机器人的个人使用，作者不对任何账号损失负责。
